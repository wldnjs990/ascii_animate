# 아스키 영상 플레이어의 동작 원리

유튜브 링크 하나가 터미널의 움직이는 글자 그림이 되기까지, `ascii_play.py`가 하는 일을 순서대로 설명합니다. 마지막에 웹 버전이 어떻게 다른지도 다룹니다.

## 1. 전체 흐름

```
유튜브 링크
   │  ① yt-dlp: 영상 파일(mp4)로 내려받기
   ▼
영상 파일 ─────────────────────────────┐
   │  ② ffmpeg: 프레임을 하나씩 풀어서       │  ⑤ ffplay: 소리 재생
   │     글자 격자 크기(예: 200x56)로 축소   │
   ▼                                      │
작은 RGB 이미지의 연속                      │
   │  ③ 파이썬: 각 픽셀을 글자 + 색으로 변환  │
   ▼                                      │
글자와 색 코드로 된 문자열                   │
   │  ④ 터미널에 출력 (프레임 시각에 맞춰) ◄──┘ 같은 시계로 맞춤
   ▼
화면
```

핵심 아이디어는 하나입니다. **영상을 가로 200, 세로 56 픽셀짜리 아주 작은 영상으로 줄인 다음, 픽셀 하나를 글자 하나로 바꿔 찍는다.** 나머지는 전부 이것을 빠르게, 소리와 어긋나지 않게 하기 위한 장치입니다.

## 2. 유튜브에서 영상 가져오기

이 부분은 직접 구현하지 않고 `yt-dlp`라는 오픈소스 도구에 맡깁니다(`fetch` 함수).

유튜브는 영상을 파일 하나로 보관하지 않습니다. 같은 영상을 해상도별(144p, 360p, 1080p …)로 여러 벌 만들어 두고, 화면(비디오)과 소리(오디오)도 따로 보관합니다. 브라우저의 유튜브 플레이어는 네트워크 상태에 맞는 조각을 골라 받아 재생합니다.

`yt-dlp`는 플레이어가 하는 일을 대신 합니다.

1. 영상 페이지에서 "이 영상에 어떤 형식들이 있는지" 목록을 얻습니다.
2. 조건에 맞는 비디오와 오디오를 하나씩 고릅니다.
3. 둘을 내려받아 ffmpeg로 하나의 mp4 파일로 합칩니다.

스크립트가 넘기는 조건은 이것입니다.

```
-f "bv*[height<=360]+ba/b[height<=360]/b"
```

"세로 360 이하인 것 중 가장 좋은 비디오(`bv*`) + 가장 좋은 오디오(`ba`), 없으면 360 이하의 합쳐진 형식(`b`), 그것도 없으면 아무거나"라는 뜻입니다. 360p만 받는 이유는, 어차피 가로 200~300칸으로 줄일 것이라 더 큰 해상도가 쓸모없기 때문입니다.

받은 파일은 `~/.cache/ascii_play/`에 링크의 해시값을 이름으로 저장해, 같은 링크를 다시 재생할 때는 내려받지 않습니다.

## 3. 영상을 프레임 단위로 풀기

영상 파일은 그림이 차곡차곡 들어 있는 것이 아닙니다. 용량을 줄이려고 "완전한 그림 한 장(키프레임) + 그 뒤로는 이전 그림과 달라진 부분만" 식으로 압축돼 있습니다. 이것을 다시 그림들로 풀어내는 일을 **디코딩**이라고 하고, `ffmpeg`가 담당합니다.

스크립트는 ffmpeg를 자식 프로세스로 띄우고 이렇게 요청합니다(`open_video` 함수).

```
ffmpeg -i 영상.mp4 -an
       -vf "fps=30,crop=...,scale=200:56:flags=lanczos"
       -pix_fmt rgb24 -f rawvideo -
```

| 부분 | 뜻 |
|---|---|
| `-an` | 소리는 필요 없음 (소리는 따로 재생) |
| `fps=30` | 1초에 30장씩 일정한 간격으로 내보냄 |
| `crop=...` | 터미널 화면 비율에 맞게 가장자리를 잘라 냄 |
| `scale=200:56` | 그림을 가로 200, 세로 56 픽셀로 축소 |
| `-pix_fmt rgb24` | 픽셀 하나를 R, G, B 각 1바이트(총 3바이트)로 표현 |
| `-f rawvideo -` | 압축하지 않은 날것 그대로 표준 출력으로 내보냄 |

여기서 중요한 점은 **프레임 하나의 크기가 항상 똑같다**는 것입니다. 200x56 격자라면 한 프레임은 정확히 200 × 56 × 3 = 33,600바이트입니다. 그래서 파이썬은 구분자 없이도 파이프에서 33,600바이트씩 끊어 읽으면 그게 프레임 한 장입니다(`read_exact` 함수).

```
[프레임 0: 33,600바이트][프레임 1: 33,600바이트][프레임 2: ...
```

한 프레임 안에서는 왼쪽 위부터 오른쪽으로, 한 줄이 끝나면 다음 줄로 픽셀이 이어집니다. `y`번째 줄 `x`번째 칸의 빨강 값은 `frame[(y * 200 + x) * 3]`에 있습니다.

### 왜 세로가 56인가: 글자 칸은 정사각형이 아니다

16:9 영상을 가로 200으로 줄이면 세로는 112여야 할 것 같지만, 터미널의 글자 한 칸은 세로가 가로의 약 2배입니다. 112줄로 찍으면 그림이 위아래로 2배 늘어나 보입니다. 그래서 세로를 절반으로 줄입니다.

```
세로 줄 수 = 가로 칸 수 × (영상 세로 / 영상 가로) × 0.5
          = 200 × (9 / 16) × 0.5 ≈ 56
```

코드에서는 `CHAR_ASPECT = 0.5`가 이 보정값이고, `grid_size` 함수가 계산합니다.

## 4. 픽셀을 글자로 바꾸기

### 밝기 구하기

픽셀의 색(R, G, B)에서 "얼마나 밝은가"를 숫자 하나로 구합니다.

```
밝기 = 0.299 × R + 0.587 × G + 0.114 × B     (0 ~ 255)
```

세 색을 똑같이 평균 내지 않는 이유는 사람 눈이 초록에 가장 민감하고 파랑에 가장 둔감하기 때문입니다. 같은 세기라도 초록이 훨씬 밝게 보입니다.

### 밝기를 글자로

글자마다 칸을 채우는 잉크의 양이 다릅니다. 공백은 아무것도 없고, `.`은 점 하나, `@`는 칸을 거의 다 채웁니다. 글자들을 잉크가 적은 것부터 많은 것 순으로 늘어놓은 것을 **램프(ramp)**라고 합니다. 이 스크립트는 69단계짜리 램프를 씁니다.

```
 .'`^",:;Il!i><~+_-?][}{1)(|/tfjrxnuvczXYUJCLQ0OZmwqpdbkhao*#MW&8%B@$
↑ 어두움                                                      밝음 ↑
```

밝기 0~255를 램프의 0~68번 자리로 옮기면 끝입니다.

```
자리 = 밝기 × 68 // 255
```

| 픽셀 (R, G, B) | 밝기 | 자리 | 글자 |
|---|---|---|---|
| (0, 0, 0) 검정 | 0 | 0 | (공백) |
| (255, 0, 0) 빨강 | 76 | 20 | `]` |
| (128, 128, 128) 회색 | 128 | 34 | `n` |
| (0, 255, 0) 초록 | 149 | 39 | `X` |
| (255, 255, 255) 흰색 | 255 | 68 | `$` |

검은 배경의 터미널에서는 밝은 글자가 많이 칠해질수록 밝아 보이므로, 밝은 픽셀에 빽빽한 글자를 씁니다. 흰 배경 터미널에서는 반대여야 해서 `--invert` 옵션이 램프를 뒤집습니다.

매 픽셀마다 나눗셈을 하면 느리므로, 밝기 0~255 각각에 대한 글자를 미리 표로 만들어 두고 찾아 쓰기만 합니다(`lut`).

### 직접 해 보기

아래는 영상의 한 장면을 흑백 아스키로 찍는 가장 작은 예제입니다. 위에서 설명한 것이 전부 들어 있습니다.

```python
import subprocess, sys

RAMP = " .'`^\",:;Il!i><~+_-?][}{1)(|/tfjrxnuvczXYUJCLQ0OZmwqpdbkhao*#MW&8%B@$"
COLS, ROWS = 100, 28

# ffmpeg 에게 5초 지점의 한 장면을 100x28 흑백 픽셀로 달라고 한다.
frame = subprocess.run([
    "ffmpeg", "-v", "error", "-ss", "5", "-i", sys.argv[1],
    "-frames:v", "1", "-vf", f"scale={COLS}:{ROWS}",
    "-pix_fmt", "gray", "-f", "rawvideo", "-",
], stdout=subprocess.PIPE).stdout

for y in range(ROWS):
    row = frame[y * COLS:(y + 1) * COLS]            # 한 줄 = 100바이트
    print("".join(RAMP[v * (len(RAMP) - 1) // 255] for v in row))  # 밝기 → 글자
```

`python3 예제.py 영상.mp4`로 실행합니다. `-pix_fmt gray`를 쓰면 ffmpeg가 밝기 계산까지 해서 픽셀당 1바이트로 주기 때문에 코드가 더 짧아집니다.

## 5. 색 입히기와 터미널 제어

터미널은 글자만 받는 것 같지만, 특별한 글자열을 받으면 그것을 찍는 대신 **명령**으로 해석합니다. 이것을 ANSI 이스케이프 코드라고 하며, 모두 `ESC` 문자(`\x1b`)로 시작합니다.

| 코드 | 동작 |
|---|---|
| `\x1b[38;2;R;G;Bm` | 이후 글자의 색을 (R, G, B)로 |
| `\x1b[0m` | 색을 기본값으로 되돌림 |
| `\x1b[줄;칸H` | 커서를 그 위치로 옮김 |
| `\x1b[2J` | 화면 전체 지우기 |
| `\x1b[?25l` / `\x1b[?25h` | 커서 숨기기 / 보이기 |
| `\x1b[?1049h` / `\x1b[?1049l` | 대체 화면으로 들어가기 / 나오기 |

예를 들어 빨간 `@`를 찍으려면 `\x1b[38;2;255;0;0m@`을 출력합니다.

**움직이는 그림이 되는 원리**는 단순합니다. 프레임을 찍을 때마다 줄을 아래로 밀어 내지 않고, 커서를 화면 맨 위로 되돌려 같은 자리에 덮어씁니다. 이것을 초당 30번 하면 애니메이션으로 보입니다.

**대체 화면**은 vim이나 less가 쓰는 것과 같은 기능입니다. 재생을 시작할 때 별도의 빈 화면으로 넘어갔다가, 끝날 때 나오면 원래 터미널 내용이 그대로 돌아옵니다.

색이 있을 때는 글자가 밝기를, 색 코드가 색을 맡습니다. 어두운 빨강은 "듬성듬성한 글자 + 빨간색", 밝은 빨강은 "빽빽한 글자 + 빨간색"이 됩니다.

## 6. 소리와 화면 맞추기

소리는 `ffplay`(ffmpeg에 딸린 재생기)를 화면 없이 띄워 따로 재생합니다. 화면과 소리는 서로 대화하지 않고, **같은 시계를 본다**는 것만으로 맞춰집니다.

```
시작 시각 = 지금
i번째 프레임이 나와야 할 시각 = 시작 시각 + i / 30초
```

프레임을 그리기 전에 시계를 보고 셋 중 하나를 합니다.

- **아직 이르다** → 그 시각까지 잠깐 쉰다.
- **제때다** → 그린다.
- **한 프레임 넘게 늦었다** → 그리지 않고 버린 뒤 다음 프레임으로 넘어간다.

세 번째가 중요합니다. 터미널이 느려서 그리는 게 밀리면, 다 그리려고 버티는 대신 프레임을 건너뛰어 소리를 따라잡습니다. 그래서 터미널이 느릴 때 "소리와 어긋남" 대신 "끊김"으로 나타납니다. `--stats` 옵션은 이렇게 건너뛴 프레임 수를 보여 줍니다.

## 7. 빠르게 만들기

가로 300칸이면 한 프레임에 글자가 2만 5천 개쯤이고, 초당 30프레임이면 1초에 75만 칸입니다. 병목은 계산보다 **터미널에 보내는 글자의 양**입니다. 색 코드 하나가 `\x1b[38;2;255;128;64m`처럼 약 19바이트라서, 칸마다 붙이면 글자 1개를 찍는 데 20바이트가 듭니다.

받아 둔 영상 20초를 300칸으로 재생할 때의 출력량으로 각 기법의 효과를 쟀습니다.

| 단계 | 20초 출력량 |
|---|---|
| 매 프레임 화면 전체를 다시 그림 | 273MB |
| + 달라진 칸만 보냄 | 35.6MB |
| + 색 단계를 줄임 (기본값) | 17.8MB |

### 같은 색은 한 번만 지정

색 코드는 한 번 보내면 다음에 바꿀 때까지 유지됩니다. 옆 칸과 색이 같으면 색 코드를 다시 보낼 필요가 없습니다.

```
칸마다:   [빨강]A [빨강]B [빨강]C [파랑]D
묶어서:   [빨강]ABC [파랑]D
```

### 색 단계 줄이기

실제 영상에서는 옆 칸과 색이 "거의 같지만 아주 조금 다른" 경우가 대부분이라, 위 방법만으로는 잘 묶이지 않습니다. 그래서 색을 굵은 단계로 반올림합니다. 채널당 256단계를 16단계(4비트)로 줄이면, 비슷한 색들이 같은 값이 되어 길게 묶입니다. `--color-bits` 옵션이 이 단계를 정하고, `make_packer` 함수가 처리합니다. 눈이 민감한 초록만 한 단계 더 세밀하게 남깁니다.

### 달라진 칸만 보내기

영상의 연속된 두 프레임은 대부분 비슷합니다. 배경은 그대로고 사람만 움직이는 식입니다. 그래서 방금 화면에 그린 프레임을 기억해 두었다가, 새 프레임과 비교해 달라진 부분만 다시 보냅니다(`changed_spans` 함수).

1. 한 줄 전체가 이전과 같으면 그 줄은 건너뜁니다.
2. 다른 줄은 16칸 단위로 나눠 비교해, 달라진 구간만 찾습니다.
3. 커서를 그 구간의 시작 위치로 옮기고(`\x1b[줄;칸H`) 그 구간만 다시 찍습니다.

화면 전체가 바뀌는 장면(빠른 카메라 이동, 장면 전환)에서는 효과가 작습니다.

### 파이썬에서 칸마다 반복하지 않기

파이썬의 `for` 문은 느려서 초당 75만 번 돌리면 그것만으로 밀립니다. 그래서 칸마다 계산하는 대신, **가능한 모든 입력에 대한 답을 미리 표로 만들어 두고** C로 구현된 내장 기능으로 한꺼번에 찾습니다.

- 픽셀의 색을 16비트 숫자 하나(0~65535)로 묶습니다.
- 그 65,536가지 값 각각에 대해 "이 색이면 어떤 글자, 어떤 색 코드인지"를 시작할 때 한 번 계산해 표로 둡니다(`build_color_tables`).
- 프레임을 그릴 때는 `map(표.__getitem__, 픽셀들)`로 표에서 찾기만 합니다.

## 8. 웹 버전은 무엇이 다른가

웹 버전(`server.py` + `index.html`)도 원리는 같고, 각 단계를 맡는 주체만 다릅니다.

| 단계 | 터미널 버전 | 웹 버전 |
|---|---|---|
| 내려받기 | yt-dlp | yt-dlp (서버가 실행) |
| 프레임 풀기 | ffmpeg | 브라우저의 `<video>` 요소 |
| 격자 크기로 축소 | ffmpeg의 `scale` | 작은 캔버스에 `drawImage` |
| 픽셀 값 읽기 | 파이프에서 바이트 읽기 | `getImageData` |
| 글자로 변환 | 같은 밝기 → 램프 방식 | 같은 방식 |
| 화면에 그리기 | 터미널에 문자열 출력 | 캔버스에 `fillText` |
| 소리 | ffplay | `<video>` 요소가 재생 |
| 싱크 | 시계를 보고 맞춤 | 영상 프레임이 나올 때마다 그림 |

눈여겨볼 점 세 가지입니다.

- **싱크가 저절로 맞습니다.** 화면에 보이지 않는 `<video>` 요소가 소리를 재생하고, 브라우저가 "영상의 새 프레임이 나왔다"고 알려 줄 때(`requestVideoFrameCallback`) 그 프레임을 읽어 그립니다. 소리와 그림이 같은 영상 요소에서 나오므로 따로 맞출 필요가 없습니다.
- **색을 입히는 방법이 다릅니다.** 글자를 칸마다 색을 바꿔 가며 그리면 느립니다. 대신 한 줄을 흰색으로 한 번에 그린 뒤, 축소한 영상 프레임을 그 위에 "글자가 있는 자리에만 칠해지도록"(`source-in` 합성) 확대해서 덮습니다. 글자 모양의 구멍으로 영상의 색이 비쳐 보이는 셈입니다. 그래서 300x102 격자 한 프레임을 그리는 데 약 1.3ms밖에 걸리지 않습니다.
- **서버가 필요한 이유는 브라우저 보안입니다.** 웹 페이지는 다른 사이트(유튜브)에서 온 영상의 픽셀을 읽을 수 없습니다. 유튜브 플레이어를 페이지에 끼워 넣어도 그 안의 그림은 읽지 못합니다. 그래서 로컬 서버가 영상을 받아 "같은 출처"에서 내려 주어야 `getImageData`가 동작합니다.

## 9. 더 알아볼 것

- **더 좋은 글자 고르기**: 지금은 밝기만 봅니다. 칸 안의 모양(윤곽선의 방향)까지 보고 `/`, `\`, `|`, `_` 같은 글자를 고르면 같은 칸 수로 훨씬 또렷한 그림이 됩니다.
- **디더링**: 밝기를 69단계로 반올림하면서 생기는 오차를 옆 칸으로 넘겨, 매끄러운 그러데이션을 흉내 내는 기법입니다.
- **반 칸 문자**: `▀` 같은 문자에 글자색과 배경색을 따로 주면 한 칸에 픽셀 두 개를 넣을 수 있습니다. 해상도가 2배가 되지만 "글자 그림"의 느낌은 사라집니다.
