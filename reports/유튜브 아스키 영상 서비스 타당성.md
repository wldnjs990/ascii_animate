# 업로드는 열려 있고, 유튜브 링크는 막혀 있다

영상을 아스키 아트로 바꿔 오디오와 함께 실시간 재생하는 것은 기술적으로 가능하지만, 가능 여부와 위험은 입력 경로에 따라 정반대로 갈린다. **파일 업로드 경로는 서버 없이 브라우저만으로 구현되고**, 이용자가 권리를 가졌거나 적법하게 보유한 파일을 자기 기기에서만 처리하는 한 조사된 범위에서 가장 안전한 형태다. **유튜브 링크 경로는 공식 수단으로는 구현할 수 없다.** IFrame Player API는 재생 제어만 제공하고 프레임·픽셀·스트림을 주지 않으며, 유튜브 개발자 정책은 오디오·비디오 구성요소의 분리와 수정, 보이지 않는 플레이어 재생, 시청각 콘텐츠의 다운로드·캐시를 조항 단위로 금지한다. 서버가 yt-dlp류 도구로 영상을 가져오는 우회 경로는 동작은 하지만 약관 위반, 한국 저작권법상 복제·전송 침해와 기술적 보호조치 우회 위험, 유튜브의 상시적인 기술 차단이 한꺼번에 겹친다. 특히 한국에서는 2026년 8월 11일 시행 개정으로 침해 법정형이 7년 이하 징역 또는 1억 원 이하 벌금으로 오르고 고의 침해에 최대 5배 배상이 도입되어 이 경로의 하방 위험이 커졌다. 따라서 현실적인 제품 형태는 "파일 업로드 + 완전 클라이언트 처리"이고, 유튜브 링크는 "본인이 내려받은 자기 영상 파일을 올리게 안내"하는 수준이 계약·법률과 충돌하지 않는 한계선이다. 이 보고서는 2026년 11월 18일 기준의 배경 조사이며 **법률 자문이 아니다.** 조사 노트에서 미검증·미확인으로 남은 사항은 본문에서도 그렇게 표시했고, 사업 결정 전에 변호사 검토와 조문 원문 대조가 필요하다.

## 파일 업로드는 서버 없이 브라우저만으로 실시간 변환된다

변환 알고리즘 자체는 새로 만들 것이 없다. 표준 방식은 문자 셀 하나를 픽셀 하나처럼 취급해 평균 밝기를 문자 램프에 대응시키는 것이고, 품질을 높이려면 문자마다 6차원 형태 벡터를 미리 계산해 셀의 국소 형태에 가장 가까운 글리프를 고르는 방식을 GPU 셰이더로 돌린다 ([alexharri.com](https://alexharri.com/blog/ascii-rendering)). 이 방식의 초기 CPU 프로토타입은 아이폰에서 한 자릿수 FPS였고 병목은 문자 조회가 아니라 샘플링이었다는 것이 저자의 설명이다 ([alexharri.com](https://alexharri.com/blog/ascii-rendering)). 브라우저용 오픈소스도 이미 여럿 있다. 조사 노트는 collidingScopes/ascii(MIT, 웹캠·업로드 영상 입력), textmode.js, p5.asciify, aalib.js 등을 꼽았으나 대부분 검색 요약만 확인했고 **각 라이브러리의 유지보수 상태와 일부 라이선스는 미확인**이다 ([collidingScopes/ascii 항목](https://awesome.ecosyste.ms/projects/github.com%2Fcollidingscopes%2Fascii)). 원문을 직접 확인한 ASCILINE은 서버 코어가 AGPL-3.0-or-later, 웹 디코더가 MIT여서, 서버에 그대로 가져다 쓰면 소스 공개 의무를 별도로 검토해야 한다 ([ASCILINE](https://github.com/YusufB5/ASCILINE)).

싱크 문제는 구조적으로 풀린다. `requestVideoFrameCallback`은 새 프레임이 합성될 때마다 콜백을 실행하며 프레임의 미디어 타임스탬프(`mediaTime`)와 누적 제출 프레임 수(`presentedFrames`)를 넘겨주고, Chrome 83, Edge 83, Firefox 132, Safari 15.4부터 지원된다 ([web.dev](https://web.dev/articles/requestvideoframecallback-rvfc)). 오디오는 `<video>` 요소가 그대로 재생하고 아스키는 "지금 표시되는 프레임"에서 매번 파생시키면 되므로, 처리가 밀려도 프레임이 건너뛰어질 뿐 누적 드리프트는 생기지 않는다는 것이 조사 노트의 설계 추론이다. 다만 이 API는 엄격한 보장이 없는 best effort이고 실제 표시보다 한 vsync 늦을 수 있으며, 프레임 단위로 정확한 작업에는 WebCodecs를 쓰라는 것이 공식 안내다 ([web.dev](https://web.dev/articles/requestvideoframecallback-rvfc)).

픽셀을 읽는 데도 걸림돌이 없다. 캔버스가 오염되어 `getImageData()`가 `SecurityError`를 던지는 것은 CORS 승인 없이 다른 출처의 데이터를 그렸을 때뿐이다 ([MDN](https://developer.mozilla.org/en-US/docs/Web/HTML/How_to/CORS_enabled_image)). 이용자가 고른 로컬 파일을 `blob:` URL로 `<video>`에 연결하면 같은 출처로 취급되어 이 문제가 생기지 않는다는 것이 노트의 판단인데, **blob URL의 동일 출처 취급은 별도 출처로 확인하지 않은 일반 지식**으로 표시되어 있다.

성능 수치는 아직 추정 단계다. ASCILINE은 재생을 24~30 FPS에 맞추고 아스키 열 수 200~240을 권장하며, 그리드가 기기에 비해 크면 영상이 오디오보다 뒤처지므로 열 수를 줄이라고 안내한다 ([ASCILINE](https://github.com/YusufB5/ASCILINE)). 이는 모두 저자 자체 보고다. 160×90 그리드의 밝기 매핑은 CPU 자바스크립트로도 30fps가 나오고 병목은 계산보다 DOM 텍스트 갱신 같은 출력 쪽일 것이라는 노트의 판단은 **독립 벤치마크 없는 추정**이며, 실기기 프로토타입 측정이 필요하다. 한계도 분명하다. 브라우저가 디코딩하지 못하는 코덱·컨테이너의 파일은 클라이언트 단독 경로에서 실패한다. 대안인 ffmpeg.wasm은 2GB 입력 한계가 이슈로 보고되어 있고(해결 여부 미확인) 메모리 내 파일시스템 때문에 더 작은 파일에서도 탭이 죽는 사례가 있다 ([ffmpeg.wasm issue #623](https://github.com/ffmpegwasm/ffmpeg.wasm/issues/623)). WebCodecs의 Safari·Firefox 지원 시점은 출처끼리 충돌하므로 **MDN 호환성 표로 재확인해야 하는 미확정 사항**이다. 모바일 Safari의 자동재생 제약과 저전력 모드 동작도 확인되지 않았다.

## 유튜브 링크는 공식 경로가 없고, 우회는 약관과 차단에 걸린다

### 공식 API는 픽셀을 주지 않는다

IFrame Player API가 문서화한 기능은 큐·재생·일시정지·탐색·볼륨·속도·상태 조회와 이벤트뿐이고, 프레임·픽셀·원시 오디오·미디어 스트림에 접근하는 함수는 없다 ([IFrame Player API Reference](https://developers.google.com/youtube/iframe_api_reference)). 유튜브 임베드는 교차 출처 iframe이므로 부모 페이지가 내부 `<video>`를 캔버스에 그릴 수도 없다(브라우저 동일 출처 정책에서 나오는 결론이며 API 문서에 명시된 문장은 아니다). Data API v3도 마찬가지다. `videos` 리소스는 제목·길이·라이선스·임베드 HTML 같은 메타데이터만 주고 스트림이나 다운로드 URL 필드가 없으며, 업로드 원본 정보인 `fileDetails`조차 소유자만 조회할 수 있는 메타데이터다 ([Videos resource](https://developers.google.com/youtube/v3/docs/videos)). 기본 쿼터는 search.list 100회, videos.insert 100회, 그 밖의 엔드포인트 합산 하루 10,000단위다 ([Quota Calculator](https://developers.google.com/youtube/v3/determine_quota_cost)). 유튜브 고객센터는 타인의 영상은 다운로드할 수 없다고 밝히고, 본인이 올린 영상만 Studio에서 720p 또는 360p MP4로 받을 수 있다고 안내한다 ([YouTube Help](https://support.google.com/youtube/answer/56100?hl=en)).

### 제품 정의 자체가 개발자 정책 조문과 충돌한다

"영상 대신 아스키를 보여주고 오디오는 원본"이라는 구상은 개발자 정책의 금지 조항과 거의 일대일로 맞닿는다. 정책은 유튜브 시청각 콘텐츠의 **오디오 또는 비디오 구성요소를 분리·격리·수정하는 것**(III.I.7), 사용자가 보는 화면에 표시되지 않는 **백그라운드 플레이어에서 재생하는 기능**(III.I.9), 플레이어의 일부나 기능을 수정·차단하는 것(III.I.6), **유튜브 API 서비스 외의 기술로 시청각 콘텐츠에 접근하는 것**(III.I.14), 사전 서면 승인 없는 다운로드·캐시·저장을 금지한다 ([Developer Policies](https://developers.google.com/youtube/terms/developer-policies)). 최소 기능 요건은 임베드 플레이어 뷰포트를 200×200px 이상으로 두고, 플레이어의 어느 부분 앞에도 오버레이나 시각 요소를 두지 말며, 플레이어가 절반 넘게 보이기 전에는 자동재생하지 말라고 요구한다 ([Required Minimum Functionality](https://developers.google.com/youtube/terms/required-minimum-functionality)). 임베드 플레이어를 쓰는 순간 API 약관과 개발자 정책이 자동으로 적용된다 ([YouTube Help](https://support.google.com/youtube/answer/171780?hl=en)). 따라서 플레이어를 숨기고 오디오만 쓰는 설계와 플레이어 위에 아스키 캔버스를 덮는 설계는 둘 다 문언상 위반이다.

한국 적용본 유튜브 서비스 약관(발효일 2022년 1월 5일)도 같은 방향이다. 서비스가 명시적으로 승인했거나 유튜브와 권리자의 사전 서면 허락이 있는 경우를 빼고는 콘텐츠의 접근·복제·다운로드·변경·수정을 금지하고, 복제를 막는 기능의 우회와 스크래퍼 같은 자동화 수단 접근을 별도로 금지한다 ([YouTube 서비스 약관](https://www.youtube.com/t/terms?hl=ko&gl=KR)). 상업적 운영 자체가 금지되는 것은 아니지만, 임베드 플레이어 시청에 요금을 받을 수 없고 광고를 팔려면 유튜브 데이터 없이도 성립하는 독립적 가치가 같은 페이지에 있어야 한다 ([Developer Policies](https://developers.google.com/youtube/terms/developer-policies)). 문언상 허용되는 형태는 공식 플레이어를 가리지 않고 보이게 둔 채, 유튜브 영상의 픽셀이나 오디오 샘플에서 파생되지 않은 것을 옆에 표시하는 것으로 한정된다. 이는 금지 조항의 반대해석이며, 플레이어 옆 콘텐츠의 허용 범위를 직접 규정한 조항은 없다. 크리에이티브 커먼즈 표시 영상이라고 달라지지도 않는다. 개발자 정책의 다운로드·분리 금지 조문에는 CC 영상이나 소유자 본인 영상에 대한 예외 문구가 없다 ([Developer Policies](https://developers.google.com/youtube/terms/developer-policies)).

### 서버 추출은 동작하지만 상시 깨지는 경로다

공식 경로 밖에서는 서버가 yt-dlp로 영상을 받아 처리하는 방법이 남는다. ASCILINE이 정확히 이 구조로, yt-dlp로 URL을 가져와 480p로 상한을 두고 캐시한다 ([ASCILINE](https://github.com/YusufB5/ASCILINE)). 그러나 운영 안정성이 낮다. 유튜브는 일부 클라이언트 요청에 PO 토큰을 요구하고, 없으면 포맷 URL 요청이 HTTP 403을 반환하거나 계정·IP가 차단될 수 있으며, 토큰은 영상 ID에 묶여 영상마다 새로 필요하다 ([yt-dlp PO Token Guide](https://github.com/yt-dlp/yt-dlp/wiki/PO-Token-Guide)). 2025년 4월에는 web 클라이언트의 HTTPS 포맷이 모두 사라지고 유튜브 자체 프로토콜인 SABR만 남았고 ([yt-dlp issue #12482](https://github.com/yt-dlp/yt-dlp/issues/12482)), yt-dlp는 자바스크립트 챌린지를 풀기 위해 Deno나 Node 같은 외부 런타임을 요구하게 되었다 ([yt-dlp EJS wiki](https://github.com/yt-dlp/yt-dlp/wiki/EJS)). 게스트 세션은 시간당 약 300개 영상에서 제한에 걸린다는 것이 yt-dlp 위키의 수치인데, 2025년 6월 편집본이라 현재와 다를 수 있다 ([yt-dlp Extractors wiki](https://github.com/yt-dlp/yt-dlp/wiki/Extractors)).

클라우드 서버에서는 문제가 더 크다. 2026년 3월의 한 개발자 경험담에 따르면 데이터센터 IP에서는 유효한 쿠키가 있어도 봇 확인 오류가 났고, 가정용(residential) 프록시를 붙인 yt-dlp만 성공했으며, 프록시 단가는 종량제 GB당 3.50달러였다 ([dev.to](https://dev.to/osovsky/i-was-building-a-cloud-video-service-youtube-turned-me-into-an-ip-trafficker-1l9o)). 이것은 **개인 한 명의 보고이고 정량 실패율은 없으며**, yt-dlp 공식 문서에서 데이터센터 IP 차단을 직접 서술한 부분은 찾지 못했다. yt-dlp의 SABR 다운로더가 2026년 11월 현재 정식 릴리스에 들어갔는지도 **확인되지 않았다.** 터미널용 아스키 유튜브 플레이어들이 "그냥 되는" 이유는 추출이 이용자 한 명의 가정용 IP에서 일어나기 때문이고, 같은 호출을 중앙 서버로 옮기면 IP 평판·레이트 리밋·토큰 문제가 운영자에게 집중된다는 것이 노트의 해석이다.

나머지 대안도 각각 대가가 있다. 화면 캡처(`getDisplayMedia`)는 매번 이용자의 공유 확인과 대상 선택을 거치고, 탭 오디오는 Chrome의 탭 공유에서만 제공된다 ([MDN](https://developer.mozilla.org/en-US/docs/Web/API/Screen_Capture_API/Using_Screen_Capture), [Chrome for Developers](https://developer.chrome.com/docs/web-platform/screen-sharing-controls)). 원본 영상이 다른 탭에 실제로 떠 있어야 하므로 "원본 대신 아스키만"이라는 요구와도 부분적으로 어긋난다. 조사 노트는 이 방식도 III.I.7과 III.I.14에 해당한다고 읽는 것이 자연스럽다고 보았으나, **유튜브가 화면 캡처 기반 재렌더링을 허용하거나 금지한다고 밝힌 공식 문서나 집행 사례는 찾지 못했다.** 브라우저 확장은 기술적으로 가장 안정적일 것으로 추정되지만(일반 지식에 의한 추정, 미검증) 웹 서비스가 아닌 설치형 제품이 되고, 약관·우회 수단 제공 문제에서 벗어나지 못한다.

### 집행은 약관 서한에서 기술 차단으로 옮겨 갔다

유튜브와 구글의 직접 조치는 저작권이 아니라 약관 위반을 근거로 한 중지 요구 서한이었다. 디스코드 음악 봇 Groovy는 서한을 받고 2021년 8월 30일 종료했고 ([9to5Google](https://9to5google.com/2021/08/25/youtube-nukes-popular-groovy-bot-discord-music-service-for-breaking-platforms-tos/)), Rythm이 같은 방식으로 뒤따랐으며 ([NME](https://www.nme.com/news/discord-music-bot-rythm-follows-groovy-into-the-void-after-cease-and-desist-3045407)), Invidious는 2023년 6월 7일 기한의 서한을 받았으나 API를 쓰지 않는다며 거부했다 ([TorrentFreak](https://torrentfreak.com/youtube-orders-invidious-privacy-software-to-shut-down-in-7-days-230609/)). 소송은 음반 업계가 맡았다. 스트림 리핑 사이트 FLVTO.biz와 2conv.com 운영자는 2022년 약 8,300만 달러 배상 판결을 받았다 ([Music Business Worldwide](https://www.musicbusinessworldwide.com/labels-awarded-83m-in-lawsuit-against-operator-of-stream-ripping-sites123456/)). 오디오만 원본으로 들려주는 아스키 서비스는 구조상 Groovy·Rythm 유형에 가장 가깝다는 것이 노트의 평가다. 다만 **아스키·필터·시각화처럼 영상을 재렌더링하는 서비스를 직접 겨냥한 집행 사례는 찾지 못했고**, 정책 위반으로 특정 API 키가 회수된 구체 사례도 확인되지 않았다. 계약상으로는 유튜브가 통지 의무 없이 API 접근을 정지·종료할 수 있다 ([API Services ToS](https://developers.google.com/youtube/terms/api-services-terms-of-service)).

## 한국 저작권법에서는 오디오와 서버 복제가 위험의 중심이다

### 2026년 개정이 하방 위험을 키웠다

2026년 8월 11일 시행 개정으로 복제·공중송신 등 직접 침해의 법정형이 **5년 이하 징역 또는 5천만 원 이하 벌금에서 7년 이하 징역 또는 1억 원 이하 벌금**으로 올랐고, 고의 침해에는 법원이 인정 손해액의 **최대 5배**까지 배상액을 정할 수 있게 되었다 ([DKL Letter](https://maily.so/dklnews/posts/g0zml17wrql), [법무법인 세종](https://shinkim.com/kor/media/newsletter/3154)). 배상액 산정에는 침해 이후 침해자가 취한 조치가 고려되고, 영리 목적으로 불법복제물 링크를 알면서 게시하는 행위는 침해로 간주된다 ([DKL Letter](https://maily.so/dklnews/posts/g0zml17wrql)). 국가법령정보센터는 현행법을 "시행 2026. 10. 29., 법률 제21595호"로 표시하는데 ([law.go.kr](https://www.law.go.kr/LSW/lsInfoP.do?lsId=000798&ancYnChk=0)), **이 2026년 4월 28일자 개정의 내용은 확인하지 못했다.** 또한 조사 노트는 법령정보센터 조문 본문을 직접 열람하지 못해 조문 번호와 문언을 2차 자료에 의존했다고 밝히고 있으므로, 아래 조문 인용은 원문 대조가 필요하다.

### 아스키 변환은 복제로 평가될 가능성이 높고, 오디오에는 변형 논거가 없다

대법원은 2차적저작물이 되려면 사회통념상 새로운 저작물이 될 정도의 수정·증감으로 새로운 창작성이 더해져야 하고, 다소의 수정·증감에 그치면 독자적 저작물이 아니라고 본다 ([대법원 2007다63409](https://www.nepla.ai/case/대법원/2007다63409)). 알고리즘이 자동으로 표현 형식만 바꾸는 아스키 변환은 이 기준을 채우기 어려워, 원 영상의 창작적 표현이 식별되는 한 복제로 평가될 가능성이 높다는 것이 노트의 추론이다. 2차적저작물로 보더라도 허락 없는 작성이므로 결론은 같다. **필터·아스키·픽셀아트 같은 자동 스타일 변환을 직접 판단한 한국 판례는 찾지 못했다.** 일시적 저장도 복제에 해당한다는 점은 대법원이 확인했다 ([대법원 2015다1017](https://www.law.go.kr/LSW/precInfoP.do?precSeq=186280)).

실질적으로 가장 큰 위험은 오디오다. 영상을 아무리 바꿔도 오디오는 원본 그대로이므로 변형 논거가 전혀 통하지 않고, 뮤직비디오 하나에는 영상저작물, 음악저작물, 실연, 음반의 권리가 겹쳐 있다는 것이 노트의 정리다(권리 조문 지도는 미검증·배경지식으로 표시됨). 앞 절의 집행 이력에서 소송을 주도한 쪽이 음반 업계였다는 사실이 이 평가를 뒷받침한다. 저작자의 동일성유지권도 문제될 수 있으나, 이용자가 필터임을 알고 보는 구조라 방어 논거가 있고 결과는 불확실하다는 것이 노트의 판단이다.

### 예외 규정은 클라이언트 처리만 덮는다

사적복제(제30조)는 공표된 저작물을 영리 목적 없이 개인적으로 또는 가정 및 이에 준하는 한정된 범위에서 이용하는 경우 이용자의 복제를 허용한다 ([로톡 법률가이드](https://www.lawtalk.co.kr/posts/44627)). 대법원은 프로그램 작동에 불가피하게 따르고 독립한 경제적 가치가 없는 일시적 복제를 면책 범위로 보았다 ([대법원 2015다1017 해설](https://korea.legal/wiki/2015%eb%8b%a41017/)). 이용자가 적법하게 가진 파일을 자기 브라우저에서만 변환하는 구조는 이 두 규정으로 설명되는 전형적 범위이고, 서버로 보내지 않으면 서비스 측의 복제·전송 행위 자체가 없다. 다만 결과물을 공유·게시하면 범위를 벗어나고, 제30조가 개변까지 허용하는지는 **원문 확인이 필요한 미검증 사항**이다. 불법 파일임을 알면서 받는 것은 적법한 사적복제가 아니라는 하급심 결정도 있다 ([법률신문](https://www.lawtimes.co.kr/news/articleViewAmp.html?idxno=48365)).

서버가 유튜브에서 영상을 받아 변환·송신하면 사정이 달라진다. 복제의 주체가 사업자로 평가될 가능성이 높아 사적복제를 원용하기 어렵다는 것이 노트의 추론이다. 이에 가장 가까운 한국 선례로 인터넷 TV 녹화 대행 서비스 사건이 언급되지만 **사건번호와 판시 모두 확인하지 못한 미검증 사항**이므로 인용 전 반드시 확인해야 한다. 공정이용(제35조의5)은 이용 목적, 저작물 성격, 이용 분량, 시장 영향의 네 요소로 판단하는데 ([korea.legal](https://korea.legal/wiki/%ec%a0%80%ec%9e%91%ea%b6%8c%eb%b2%95-%ec%a0%9c35%ec%a1%b0%ec%9d%985/)), 감상 목적이 원작과 같고 영상 전편과 오디오 전부를 쓰며 원작 시청을 대체할 수 있으므로 네 요소 모두 불리하다는 것이 노트의 평가다. 미국 기준으로도 같다. 연방대법원은 Warhol 판결에서 새로운 표현이나 미감을 더한 것만으로는 부족하고 이용 목적이 원작과 실질적으로 같고 상업적이면 불리하다고 했고 ([Wiley](https://www.wiley.law/alert-Copyright-Fair-Use-Purpose-and-Character-SCOTUS-Says-Transformation-Alone-Isnt-Enough)), 제9순회항소법원은 이용자가 고른 필터를 적용해 영화를 스트리밍한 VidAngel에 대해 공정이용을 인정하지 않았다 ([US Copyright Office](https://www.copyright.gov/fair-use/summaries/disney-vidangel-9thcir2017.pdf)). **제35조의5를 스타일 필터나 리믹스 도구에 적용한 한국 판례는 찾지 못했다.**

### 기술적 보호조치 우회는 침해와 별개의 책임이다

저작권법 제104조의2는 정당한 권한 없이 접근통제형 기술적 보호조치를 무력화하는 행위와, 무력화를 주된 목적으로 하는 장치·서비스의 제공을 금지한다 ([korea.legal](https://korea.legal/wiki/%ec%a0%80%ec%9e%91%ea%b6%8c%eb%b2%95-%ec%a0%9c104%ec%a1%b0%ec%9d%982/)). 이 책임은 저작권 침해와 별개여서, 대상이 CC 영상이거나 결과물이 공정이용이어도 따로 문제될 수 있다는 것이 노트의 해석이다. 유튜브의 롤링 사이퍼가 유효한 보호조치인지에 대해 독일 함부르크 고등법원은 인정하는 방향으로 판단했다 ([heise](https://heise.de/-10179284)). 미국에서는 Yout v. RIAA 1심이 Yout의 비위반 확인 청구를 기각했고, 제2순회항소법원 항소는 2024년 2월 변론 이후 2026년 9월 9일 갱신된 도켓에 판결 기재가 없다 ([CourtListener](https://www.courtlistener.com/docket/66697744/yout-llc-v-recording-industry-association-of-america-inc/)). **그 이후 선고 여부는 확인되지 않았다.** **한국에서 유튜브 다운로더나 스트림 리핑에 제104조의2를 적용한 판결은 발견되지 않았고**, 변호사 상담 답변 수준의 견해만 있다 ([로톡 Q&A](https://www.lawtalk.co.kr/qna/596090)). 판결이 없다는 것이 적법을 뜻하지는 않는다. 벌칙 수준과 2026년 개정에 따른 변경 여부는 미검증이다.

### 서버가 가져와 변환하면 면책 조항 밖으로 나간다

온라인서비스제공자 책임 제한(제102조)은 송신을 시작하지 않고, 저작물을 선택하지 않으며, 내용을 수정하지 않는 것을 전제로 한다 ([korea.legal](https://korea.legal/wiki/%ec%a0%80%ec%9e%91%ea%b6%8c%eb%b2%95-%ec%a0%9c102%ec%a1%b0/)). 서비스가 스스로 유튜브에서 영상을 가져와 아스키로 바꾸면 이 전제에서 벗어나 직접 침해 주체로 평가될 위험이 크다는 것이 노트의 해석이며, 이를 명시한 판례는 확인되지 않았다. 반면 이용자 브라우저에서 이용자 파일만 처리하는 도구에 남는 위험은 방조다. 대법원 전원합의체는 링크 사안에서 침해에 대한 충분한 인식과 영리적·계속적 행위를 요구했고 ([법률신문](https://www.lawtimes.co.kr/news/articleView.html?idxno=172826)), 미국 연방대법원도 2026년 3월 Cox 판결에서 침해를 유인했거나 서비스가 침해에 맞춰 설계된 경우에만 기여책임을 인정했다 ([Digital Music News](https://www.digitalmusicnews.com/2026/04/13/yout-v-riaa-cox-decision/)). 조사 노트는 Cox 판결문 원문이 아니라 요약 보도에 의존했다. 범용 필터 도구는 이 기준과 거리가 멀지만, "유튜브 뮤직비디오를 아스키로" 같은 홍보 문구는 유인의 증거가 될 수 있다. youtube-dl 삭제 요청에서도 README의 저작권 음악 영상 예시가 근거 중 하나였다 ([EFF](https://www.eff.org/deeplinks/2020/11/github-reinstates-youtube-dl-after-riaas-abuse-dmca)).

저위험 콘텐츠에도 단서가 붙는다. 본인 영상이라도 배경음악이나 타인의 실연은 별개 권리다. 유튜브의 CC 옵션은 CC BY이고 개작과 상업적 이용이 허용되지만 ([YouTube Help](https://support.google.com/youtube/answer/2797468?hl=en)), 모든 CC 라이선스는 출처표시를 요구하며 ([CC 위키](https://wiki.creativecommons.org/Best_practices%20_for_attribution)) 변경금지(ND) 조건이 붙은 저작물은 개작물 공유가 금지된다 ([Penn State](https://copyright.psu.edu/copyright-basics/creative-commons)). 무엇보다 CC 라이선스는 저작권 이용허락일 뿐 유튜브 약관과 우회 문제를 풀어주지 않으므로, CC 영상도 유튜브 밖에서 구한 원본 파일이나 창작자가 직접 내려받은 파일로 다뤄야 한다. 유튜브가 적용하는 CC BY의 버전은 확인되지 않았다.

위험 완화 조치로 조사 노트가 정리한 것은 URL 입력 미지원과 파일 업로드 한정, 원본·변환물 미저장, 업로드물에 대한 이용자 권리 보증, 신고·삭제 절차와 수령인 공지, 특정 플랫폼이나 저작권 콘텐츠를 내세우지 않는 마케팅, CC·퍼블릭 도메인 샘플 제공이다. 이 목록은 **개별 서비스 약관을 확인하지 않은 일반론**으로 표시되어 있다. 이용자 보증은 서비스가 직접 침해 주체가 되는 경우 권리자에 대한 책임을 없애지 못하고 구상 근거에 그친다.

## Conclusion

세 갈래 조사가 한 지점에서 만난다. 기술, 유튜브 계약, 저작권법이 각각 독립적으로 "서버가 유튜브에서 가져오는 순간"을 경계선으로 지목한다. 브라우저 보안 모델은 임베드 픽셀을 막고, 개발자 정책은 분리와 수정을 조문으로 금지하며, 저작권법은 복제 주체가 사업자로 바뀌는 지점에서 예외 규정과 면책을 거둔다. 그래서 이 구상의 성패는 변환 알고리즘이 아니라 **"링크 붙여넣기"라는 편의를 포기할 수 있는가**에 달려 있다. 포기하면 서버 비용도 법적 노출도 거의 없는 클라이언트 도구가 되고, 고집하면 확인된 선례가 모두 권리자 쪽으로 기운 영역에 들어간다.

다음 단계는 두 가지다. 기술 쪽에서는 실기기에서 그리드 크기별 프레임률과 드롭률을 재는 프로토타입이 독립 벤치마크의 공백을 메운다. 법률 쪽에서는 변호사 검토 전에 조문 원문 대조, 법률 제21595호의 개정 내용, 녹화 대행 서비스 선례, Yout 항소심 선고 여부를 확인해야 한다. 이 네 가지가 본 조사에서 결론에 영향을 줄 수 있는 채로 남은 미확인 사항이다. 이 문서는 배경 조사이며 법률 자문을 대신하지 않는다.
